# Wikontic Lite

Wikontic Lite преобразует текст в граф знаний: сущности и отношения между ними,
связанные с исходными фрагментами. Результат можно проверить, исправить и сохранить
в JSON для дальнейшей работы с базой знаний.

Проект разрабатывается в рамках курса ML System Design. В ДЗ №1 подготовлены
постановка и окружение разработки, в ДЗ №2 — сопоставление данных, EDA и подробный
план обучения и оценки. Модель и сервис пока не реализованы.

## Сценарий использования

Например, исследователь готовит обзор технологий по англоязычным аннотациям
и фрагментам статей. Ему нужно собрать связи между методами, задачами и компонентами
для предметной базы знаний. Wikontic Lite предлагает факты с исходными фрагментами;
исследователь проверяет их, исправляет ошибки, добавляет пропуски и экспортирует JSON.
Другой возможный сценарий — структурирование открытых описаний библиотек:
поддерживаемые форматы и зависимости компонентов.

Небольшой корпус подходит для обзора узкой темы или очередного пополнения базы:
время уходит не только на чтение, но и на выписывание и проверку отдельных связей.
Для одного короткого текста ручная работа может оказаться проще. Пользу этих
сценариев ещё предстоит проверить в пилоте.

Модель будет генерировать JSON с триплетами и evidence. Приложение проверит структуру
и координаты источников, покажет факты для редактирования и сформирует итоговую
выгрузку. В первой версии достаточно одного приложения с интерфейсом, API и модулем
инференса, без отдельной графовой СУБД. Учитель используется только офлайн для обучения.

### Пример формата результата

Для текста `Marie Curie was born in Warsaw.` с идентификатором `demo-001`
предусмотрен следующий формат ответа. Это пример контракта будущего сервиса.

```json
{
  "document_id": "demo-001",
  "triples": [
    {
      "subject": "Marie Curie",
      "predicate": "was born in",
      "object": "Warsaw",
      "evidence": {
        "text": "Marie Curie was born in Warsaw.",
        "start": 0,
        "end": 31
      }
    }
  ]
}
```

`start` и `end` задают границы фрагмента в символах исходной Python-строки:
начало включается, конец — нет. В этом примере `text[0:31]` совпадает с
`evidence.text`. Соответствие координат проверяется отдельно от того, действительно
ли фрагмент подтверждает отношение.

## Основа проекта

Проект продолжает работу над [Wikontic](https://github.com/screemix/Wikontic) —
системой построения графов знаний с привязкой к онтологии Wikidata.
В [ветке distillation](https://github.com/screemix/Wikontic/tree/distillation)
собраны предыдущие эксперименты с SmolLM2-1.7B-Instruct, QLoRA и Focal Loss.

В Wikontic Lite основное внимание уделяется компактной модели извлечения фактов,
независимой оценке качества и удобству проверки результата. Дистилляция касается
извлечения: онтологическое выравнивание и глобальное разрешение сущностей остаются
за пределами первой версии.

В отличие от прежних экспериментов, качество student будет оцениваться по независимой
разметке, а не по совпадению с ответами учителя. Кандидат публичного OpenIE-бенчмарка —
[CaRB](https://github.com/dair-iitd/CaRB); для проверки документных фактов и источников
также планируется ручной эталон. Выбор модели, метода обучения и окончательного
набора бенчмарков относится к ДЗ №2.

Требования, архитектура и протокол оценки описаны в
[дизайн-документе](docs/ml_system_design_doc.md).

## Установка

Для разработки используется Python 3.12 и `venv + pip`.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-dev.txt
python -m pip install --no-deps --no-build-isolation -e .
```

Если `.venv` уже существует, достаточно активировать его и установить зависимости.
Пока пакет содержит только каркас: GPU, ключи API, базы данных и ML-библиотеки для
его установки не требуются. Прямые версии инструментов закреплены в
`requirements-dev.txt`; транзитивный lock-файл пока не добавлен.

## Данные для ДЗ №2

Учительские дампы HotpotQA и MuSiQue размещаются локально в `data/teacher/`.
Они не входят в GitHub-репозиторий. Набор размещается на Hugging Face Datasets:
[bl4ckse4m/wikontic-lite-teacher-data](https://huggingface.co/datasets/bl4ckse4m/wikontic-lite-teacher-data).
Для воспроизведения закреплена ревизия `48caaeef5a103a775392a4b7fa14c90fa94e259f`.
14 ноября 2026 года все три файла проверены анонимным скачиванием этой версии:
SHA-256 совпадают с локальными дампами. Набор опубликован под CC BY-SA 4.0;
лицензия данных не определяет лицензию кода проекта.

```bash
python -m pip install huggingface_hub

HF_DATASET_ID="bl4ckse4m/wikontic-lite-teacher-data"
HF_DATASET_REVISION="48caaeef5a103a775392a4b7fa14c90fa94e259f"
hf download "$HF_DATASET_ID" \
  --repo-type dataset \
  --revision "$HF_DATASET_REVISION" \
  --include "kg_dump*.json" \
  --local-dir data/teacher
```

Команда предполагает, что три JSON лежат в корне Dataset. Для публичного
негейтированного набора авторизация обычно не требуется; для private/gated
сначала потребуется `hf auth login` и разрешение на доступ. Токены не должны
попадать в README или конфигурации проекта.

Ожидаемые локальные имена:

```text
data/teacher/
  kg_dump_hotpot_gpt4_1_onto_triplets.json
  kg_dump_musique_gpt4_1_onto_triplets.json
  kg_dump_triplets_musique_train_split_occ_openai_gpt_oss_120b_onto.json
```

Имя HotpotQA-файла на HF должно совпадать с указанным выше. Переименование не
должно менять содержимое: контрольные суммы дампов сохранены в
`reports/source_matching.json`. Закреплённая ревизия позволяет повторить анализ
даже после обновления Dataset.

Загрузка исходных QA-текстов и сопоставление с дампами выполняются отдельно
от dev-проверок:

```bash
python -m pip install -r requirements-data.txt
python scripts/download_qa_sources.py
python scripts/match_teacher_sources.py
```

Исходные файлы сохраняются в `data/raw/`, восстановленные контексты —
в `data/processed/`. Эти каталоги исключены через `.gitignore`.
Источники, лицензии, результаты и ограничения описаны в
[отчёте сопоставления данных](reports/source_matching.md).

### EDA

```bash
python -m pip install -r requirements-eda.txt
python scripts/eda.py --seed 42
python -m unittest discover -s tests -v
```

EDA использует файлы предыдущего шага и выполняется на CPU. Результаты:
[отчёт с семью графиками](reports/eda/README.md),
[диагностический разбор 30 примеров](reports/eda/diagnostic_review.md)
и агрегированные таблицы в `reports/eda/tables/`. Локальные тексты выбранных
примеров, подробные длины и кандидат группового разбиения находятся
в `data/processed/eda/`, не в публичных артефактах.

Восстановлено 38 839 контекстных записей и обнаружены повторы между источниками,
37 структурно невалидных SPO, 4 пустых ответа и отсутствие evidence. Пробная
train/validation не имеет общих нормализованных текстов и заголовков, но не
является независимым тестом. Полный план очистки и моделей — в §2.3 дизайн-документа.

## Проверки

```bash
ruff check .
ruff format --check .
pre-commit validate-config
```

Ruff проверяет весь Python-код проекта. Отображение Mermaid-схем в дизайн-документе
и корректность примеров проверяются отдельно.

Для автоматического исправления и форматирования:

```bash
ruff check --fix .
ruff format .
```

### pre-commit

```bash
pre-commit install
pre-commit run --all-files
```

Хуки запускают Ruff, проверяют YAML и TOML, убирают лишние пробелы, нормализуют
конец файла и проверяют маркеры конфликтов и большие файлы. Ruff lint с исправлениями
выполняется перед форматированием. Новые неотслеживаемые файлы могут не попасть в
`--all-files`, поэтому их нужно предварительно добавить в index.

### CI

GitHub Actions запускает проверки на push в `main`, `hw_1` и `hw_2`, а также на PR
в эти ветки. Отдельная CPU-задача запускает unit-тесты логики EDA на небольших
синтетических примерах. Полный EDA в CI не выполняется: для него нужны локальные
учительские данные. Workflow не требует моделей, GPU и секретов.
Статус конкретного запуска доступен во вкладке Actions.
